# iBuilder

The vendor site theme for the eight iBuilder WordPress plugins sold on
Codester. A child of **WPWiseBones**, like RealWise, AEC Forge and Becoming.

**Version:** 1.0.0 · **Slug / text domain:** `ibuilder` ·
**Prefix:** `ibuilder_site_` (functions) · `IBUILDER_SITE_` (constants) ·
`ibs-` (CSS) · **Template:** `wpwisebones`

The prefix is `ibuilder_site_` rather than `ibuilder_` on purpose: the eight
plugins already own `ibuilder_<product>_` across 25 global functions, and a
theme that squatted on the bare prefix would collide the first time somebody
installed a plugin and this theme on the same site. Checked before choosing.

---

## What it is, and what it deliberately is not

**Is:** a product site. A front page that presents the catalogue, a page per
plugin, Documentation, Support and About, and links out to the Codester
listing and the public demo.

**Is not a storefront.** The sibling RealWise theme ships Easy Digital
Downloads with license-enabled products. This one ships no EDD, no WooCommerce
dependency and no licence API, for a reason worth keeping:

1. Selling happens on Codester. A second checkout is work with no revenue.
2. All eight readmes advertise no licence key, no activation and no
   phone-home, and Codester rejects "activation systems, purchase-code checks,
   domain locks or remote license validation" outright. A licence-issuing
   storefront on the vendor's own site would read, in public, as contradicting
   the pitch.

It also makes **no outbound HTTP request of any kind** — system fonts only, no
Google Fonts, no CDN. AEC Forge loads Archivo from Google and is right to; a
site whose entire claim is "these plugins never phone home" cannot.

## Setup

1. Install WPWiseBones (the parent) and activate **iBuilder**.
2. **Appearance → iBuilder Setup → Build the iBuilder site.**
3. Optionally set the demo URL on the same screen, or in `wp-config.php`:

   ```php
   define( 'IBUILDER_SITE_DEMO_URL', 'https://demo.wpibuilder.com' );
   ```

   The constant wins over the setting. Until one is set, every demo button is
   **hidden** rather than rendered dead — the site is complete without a demo.

The build creates Home (as the static front page), a page per plugin on the
*iBuilder Product* template, and Documentation / Support / About, then builds
and assigns the primary and footer menus. It is idempotent: pages are matched
on a hidden meta flag rather than on title, so renaming one in the editor does
not produce a duplicate on the next build. Verified by building three times —
page count, menu count and menu items were unchanged.

**A rebuild overwrites page content.** That is the trade for having the copy
generated; the admin screen says so too.

## Generated files — do not hand-edit

| File | Generated by | Holds |
|---|---|---|
| `inc/products.php` | `codester/tools/make_site_products.py` | name, tagline, price, icon, 4 features per product |
| `inc/descriptions.php` | the same | the long per-product copy and requirements |

Both come from `C:\Server\codester\_listing-kits\<slug>\listing.md` — the same
source the Codester upload sheet and the form fillers read. The site and the
listing therefore cannot disagree about a price. Re-run after editing a kit:

```bash
python C:\Server\codester\tools\make_site_products.py
```

`products.php` is lean (~10 KB) because it loads on every request.
`descriptions.php` (~45 KB) is loaded **only** by the site builder, which
writes it into page content once.

The one field not generated is `codester_url`. Nothing is submitted yet, so
every product falls back to the seller profile and its button honestly reads
"See it on Codester" rather than "Buy". Fill them in as listings go live — the
generator preserves anything you set — or override with the
`ibuilder_site_product_url` filter.

## The parent-stylesheet trap

Worth reading before changing any CSS, and it applies to **every** child of
WPWiseBones.

The parent enqueues `get_stylesheet_uri()`, which resolves to the *child's*
`style.css` once a child is active. So `wpwisebones/style.css` — 12 KB
carrying the site header, navigation, footer, skip link, back-to-top,
breadcrumbs and `#content` padding — **never loads under any child theme.**
The parent's `assets/css/main.css` does still load, and covers core block,
gallery, alignment, form and `screen-reader-text` styles.

Measured in a real install with this theme active, before the fix:

| | Was | Should be |
|---|---|---|
| `#primaryNavbar` (open mobile menu) | `background: rgba(0,0,0,0)`, `padding: 0` | white panel, 1rem |
| `#back-to-top` | `position: static` — sat in the footer, bottom-left | `fixed`, bottom-right, hidden until scrolled |
| `.site-header` with `body.sticky-header` | `position: relative` — sticky silently did nothing | `fixed`, with body padding to match |

The transparent mobile menu was the bad one: it rendered invisibly on top of
the hero, so the page looked like the toggle did nothing.

All three are now in `assets/css/ibuilder.css` under "Chrome the parent's
style.css would have provided", ported in the brand palette rather than by
re-enqueuing the parent stylesheet — that file also carries the base colours
this theme deliberately replaces.

**56 selectors exist only in the parent's `style.css`.** This theme covers the
ones it uses. It does not use the companion plugin's `wpb-*` shortcodes, blog
comments or the landing template, so those are not ported; add them here if you
start using them, rather than expecting the parent to supply them.

## Layout

```
ibuilder/
├── style.css                      theme header only — brand CSS is in assets/
├── functions.php                  version, demo URL, enqueue, favicon, OG
├── front-page.php                 hero, catalogue, trust strip, close
├── footer.php                     branded footer (also closes the parent's #page)
├── page-templates/product.php     "iBuilder Product" — branded head + buy card
├── inc/products.php               GENERATED
├── inc/descriptions.php           GENERATED
├── inc/site-builder.php           Appearance → iBuilder Setup
├── assets/css/ibuilder.css        the whole skin, plus the chrome above
├── assets/img/mark.svg            favicon fallback
├── assets/img/og-default.png      1200×630 social preview
└── screenshot.png                 1200×900
```

`footer.php` must close `<div id="page">`, which the parent's `header.php`
opens and never closes — measured: the parent's header leaves exactly one div
open and its footer closes exactly one extra. It also re-implements the
back-to-top button, because overriding a footer silently drops whatever it was
carrying.

## Tested

Built in a throwaway WordPress 7.1.4 install with `WP_DEBUG` on:

* Both themes detected; `get_template()` = `wpwisebones`, `get_stylesheet()` =
  `ibuilder`
* Build created 12 pages, set the static front page, built 2 menus with the
  eight plugins nested under a Plugins parent
* All six page types render 200 with **zero** PHP notices, warnings or errors —
  `debug.log` stayed empty
* Markup balanced: 50 `<div>` / 50 `</div>` on the front page
* Three consecutive builds left page count, menu count and menu items unchanged
* Demo URL guard rejects a bare hostname, `javascript:` and `ftp://`, accepts
  `http(s)` and strips a trailing slash
* Mobile (375×812) verified visually after the chrome fix
